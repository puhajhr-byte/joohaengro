# 프렙 카페 운영 관리 웹 프로그램 기술 요구사항 (TRD)

> TRD(기술 요구사항 문서)는 합의된 제품·기능 요구를 어떤 기술과 운영 방식으로 구현할지 정리한다. 이 문서는 `docs/01_PRD.md`, `docs/02_FRD.md`, `디자인/` 시안을 기준으로 작성했다. **기술 설계 문서만 작성했으며 아직 코드는 구현·배포하지 않았다.**

## 1. 사용할 기술과 선택 이유

### 1.1 기술 구성

| 영역 | 제안 기술 | 선택 이유 |
|---|---|---|
| 웹 UI·서버 | Next.js App Router + React + TypeScript | 한 프로젝트에서 화면 렌더링과 서버 처리를 함께 다룰 수 있다. 읽기 화면은 서버에서 데이터를 받아 표시하고, 입력·필터 같은 상호작용만 브라우저에서 처리한다. TypeScript는 날짜·금액·단위 등 자료 형태가 맞지 않는 오류를 개발 중 줄이는 언어 도구다. |
| 스타일 | Tailwind CSS | 시안 HTML에서 유틸리티 클래스 기반 스타일을 이미 사용하고 있고, PC·태블릿·모바일 배치를 빠르게 맞추기 적합하다. |
| 데이터베이스 | Supabase PostgreSQL, 서울 리전 | 판매·메뉴·레시피·재료·비용은 서로 연결된 표 형태 자료다. 관계형 데이터베이스는 참조 관계, 중복 방지, 한 번에 여러 변경을 저장하는 트랜잭션을 제공한다. 서울 리전은 주요 사용자인 한국 점주와 가깝다. |
| 로그인 | Supabase Auth 이메일 일회용 코드(OTP) | 점주 한 명만 허용하는 로그인을 제공하고 비밀번호를 새로 관리하지 않아도 된다. OTP는 이메일로 전송하는 한 번만 쓸 수 있는 숫자 코드다. 가입은 공개하지 않고 점주 계정을 관리자가 사전 등록한다. |
| 파일 저장 | Supabase Storage 비공개 임시 저장소(수업 후 파일 기능용) | 가져오기·복원용 파일을 임시 처리할 필요가 생길 때 공개 URL 없이 접근 제한을 적용할 수 있다. MVP는 가상 자료를 미리 준비하므로 파일 업로드를 사용하지 않는다. |
| 웹 호스팅 | Vercel Pro, 서울 함수 리전 | GitHub 저장소 연결, 변경 미리보기(Preview), 운영 배포(Production)를 제공한다. 서버 함수도 데이터베이스와 같은 서울 리전으로 두어 왕복 지연을 줄인다. |
| 코드 저장·변경 이력 | GitHub | 소스 코드와 데이터베이스 구조 변경 기록을 버전 이력으로 보존하고, 배포에 연결한다. 매장 기록·백업 파일·비밀 키는 저장소에 넣지 않는다. |

Next.js App Router는 페이지·서버 렌더링·상호작용 컴포넌트를 한 앱에서 구성한다. Supabase 공식 안내는 Auth 세션을 서버 렌더링 앱의 보안 쿠키로 전달하는 방식을 제공한다. [Next.js App Router](https://nextjs.org/docs/app), [Next.js 서버/클라이언트 구성](https://nextjs.org/docs/app/getting-started/server-and-client-components), [Supabase Next.js 서버 인증](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs)

- 수업용 개발·Preview에서 가상 예시만 이용하는 경우 Free 구성은 가능하나, 실제 매장 자료를 넣기 전 Pro 운영 환경으로 옮긴다. 실제 자료를 Free 환경에 넣지 않는다.
- 요금표와 서비스 한도는 변경될 수 있으므로 실제 계정 생성 직전에 다시 확인한다. 사용량을 매월 확인하고 저장량·함수 실행·전송량 알림 및 지출 한도를 설정한다.

### 1.3 구현 범위 원칙

- PRD에서 정한 사용 순서와 MVP: 판매 입력·수정·삭제 → 메뉴 제품 수익성 → 실제 손익·비용 → 재고 잔량/최소 재고 기록 → 마감 완료 표시를 유지한다.
- PRD의 수업 후 확장 기능(엑셀/JSON 가져오기, 파일 내보내기, 백업/복원, 발주 제안, 예측, 주·분기·반기·연간 조회)은 데이터 모델과 경계를 고려하되 MVP에 포함하지 않는다.
- 시안의 가상 금액·메뉴를 계산된 실적처럼 하드코딩하지 않는다. 샘플 초기 자료에는 가상 예시 표식을 유지한다.
- 시안 버튼 중 PRD 범위에 없는 외부 주문 발송·외부 회계/결제 연동은 구현하지 않는다.

## 2. 처리 순서

### 2.1 화면 요청 및 저장 흐름

1. 사용자가 이메일 OTP로 로그인한다. 로그인하지 않았거나 허용된 점주 계정이 아니면 업무 화면·데이터에 접근하지 못한다.
2. 브라우저는 날짜·기간 및 입력값을 형식 검증한다. 이는 빠른 안내를 위한 1차 검사다.
3. 입력 저장 요청은 Next.js 서버로 전송한다. 서버는 세션과 점주 권한을 재확인하고 같은 규칙으로 값을 다시 검증한다. 브라우저 검증만 믿고 데이터베이스에 저장하지 않는다.
4. 서버의 기능별 계산 모듈은 FRD 계산 기준을 적용한다. 금액은 원화 정수 단위로 처리하고, 반올림은 표시 시점까지 미루며 내부 중간 계산의 정밀도는 보존한다. 재료 수량은 g·ml·개 기준 단위로 보존한다.
5. Supabase PostgreSQL에 기록을 저장한다. 판매 집계 병합·금액 합산, 입고/폐기 이벤트와 잔량 재계산, 실사 차이 기록은 한 트랜잭션으로 처리해 일부만 반영되는 상황을 방지한다.
6. 저장 성공 뒤 서버가 최신 저장 결과를 반환하고 화면의 목록·집계·마감 홈 요약을 갱신한다. 실패하면 기존 기록을 유지하고 입력 내용을 화면에 남겨 재시도할 수 있게 한다.

Next.js 서버 컴포넌트는 비밀 키를 브라우저에 전달하지 않고 데이터 조회를 처리하며, 버튼 이벤트·모달·필터처럼 상호작용이 필요한 부분만 클라이언트 컴포넌트로 둔다. 인증된 자료 화면은 사용자별 응답을 공유 캐시하지 않는다. Next.js 서버/클라이언트 구성과 Supabase SSR 세션 문서를 따른다. [Next.js 컴포넌트 경계](https://nextjs.org/docs/app/getting-started/server-and-client-components), [Supabase SSR 인증](https://supabase.com/docs/guides/auth/server-side)

### 2.2 계산·자료 처리 순서

- **판매:** 수량·단가·할인 검증 → 총 판매액과 순매출 계산 → 같은 날짜·메뉴·채널 행이 있으면 수량·총액·할인·순매출 합산 → 저장 → 화면 표시용 가중 평균 단가 계산. FRD 예시 `2×4,500−500=8,500원`은 검산 기준이다.
- **메뉴 수익성:** 해당 기간의 확정된 판매만 선택 → 적용 레시피 버전과 구매 가격 이력 확인 → 메뉴당 식재료 원가와 해당 채널 포장 원가 계산 → 제품 마진·마진율 집계 → 누락된 원가 기준을 0으로 바꾸지 않고 계산 불가/부분 결과 표시. 메뉴 제품 마진에서 임차료·정규 인건비·결제수수료를 빼지 않는다.
- **실제 손익:** 순매출·판매 소비 원가·확인된 실제 지출을 각각 조회 → 월 비용 계획/과거 일할 배분 행은 별도 비교 영역에 표시 → 해당 기간 실제 지출 자료가 없으면 완전한 실제 손익이라고 하지 않고 누락 상태 표시. 실제 수수료액이 주어지지 않으면 자동 추정하지 않는다.
- **재고:** 기초 수량과 재고 이벤트, 판매 집계에 따른 레시피 이론 소진을 읽음 → 이론 잔량 계산 → 실사 입력이 있으면 차이를 조정 이벤트로 저장하고 이후 잔량을 실제 수량과 맞춤 → 부족/음수는 감추지 않고 안내한다.
- **마감 승인:** 선택일의 미완료 항목 상태를 확인 → 사용자가 승인 → 완료 상태와 변경 이력 기록. 승인 뒤 정정도 기록 이력에 남긴다.

### 2.3 조회·속도 기준

- 기준 데이터(메뉴·재료·레시피·분류)는 필요한 범위에서 서버 조회 후 재사용할 수 있으나, 판매/비용/재고/마감 응답은 최신 저장값을 기준으로 한다. 계정 간 캐시 공유를 하지 않는다.
- 판매·비용·재고 조회는 전체 자료를 한 번에 브라우저로 보내지 않고 날짜·메뉴·채널/재료 조건으로 서버에서 범위를 줄인 뒤 페이지 단위로 반환한다.
- 기본 조회 인덱스는 판매 날짜·메뉴·채널, 비용 날짜·분류, 재고 날짜·재료 ID, 레시피 메뉴·버전으로 한다. 인덱스는 검색 속도를 돕는 자료 구조다.
- 현재 자료 규모(판매 6,112건, 비용 3,560건, 재고 이벤트 1,515건, 2026년 9월 현재)는 이 구성이 처리할 수 있는 소규모 단일 매장 사용량이다. 사용량이 크게 늘면 실제 조회시간과 데이터베이스 지표를 측정한 뒤 조정한다.
- 첫 사용 화면은 마감 홈의 주요 요약만 조회하고, 상세 표·차트는 해당 탭/기간을 열 때 불러온다. 비싼 분산 처리나 실시간 스트리밍은 요구되지 않아 추가하지 않는다.
- Vercel 함수와 Supabase DB를 모두 서울(`icn1`/`ap-northeast-2`)에 배치한다. Vercel 함수 기본 위치는 미국 동부이므로 명시적으로 조정해야 한다. 두 공식 리전 목록은 한국 서울을 지원한다. [Vercel 리전](https://vercel.com/docs/regions), [Supabase 리전](https://supabase.com/docs/guides/platform/regions)

구현 저장소를 만들 때 아래 구조를 사용한다. 경로는 제안 구조이며 코드는 아직 생성하지 않았다.

| `src/lib/domain/` | 금액·마진·손익·재고 계산. 입력 화면과 분리하여 계산 정의를 한 곳에서 검증한다. |

| `supabase/migrations/` | 데이터베이스 표/제약/인덱스의 변경 이력. 코드와 함께 GitHub에 보관한다. |
| `supabase/seed/` | 프렙 카페 제공 샘플을 가상 예시로 넣는 초기 자료. 실제 사용자 자료는 포함하지 않는다. |
| `docs/` | PRD·FRD·TRD·테스트 결과와 사용 정책 문서. |
| `.env.example` | 필요한 환경변수의 이름만 예시로 둔다. 실제 URL 키·비밀번호는 넣지 않는다. |

## 4. 데이터 저장·가져오기·백업·복원

### 4.1 데이터 저장과 관계

- 기준 정보: 공급사, 재료, 메뉴, 레시피 버전, 재료 가격 이력, 영업 달력.
- 운영 정보: 날짜·메뉴·채널별 판매 집계, 월 비용 계획, 실제 비용 기록, 계획에서 배분된 과거 비용, 기초 재고, 재고 변동 이벤트, 마감 상태, 변경 이력.
- 판매 집계는 `(날짜, 메뉴 ID, 채널)` 기준 중복 제한을 두고 FRD의 병합 규칙을 적용한다. 병합된 단가·할인·총액을 잃지 않도록 수량·총 판매액·할인액·순매출을 별도 저장하고 표시 단가는 합계에서 계산한다.
- 기존 판매행의 판매 당시 가격·할인·순매출·수수료·개당 원가 스냅샷은 보존한다. 새 기준 가격/레시피 변경이 과거 실적을 덮어쓰지 않는다.
- 실제 지출과 월 비용 계획/일할 배분 자료는 자료 유형을 분리한다. 계획 배분값을 실제 지출로 복제하거나 두 번 더하지 않는다.
- 재고는 현재 잔량 하나만 덮어쓰는 방식 대신 입고·폐기·실사 조정 이벤트를 기록하고, 계산 잔량과 실사 기준을 다시 만들 수 있게 한다. 실사 이벤트에는 조정 전·후 수량, 차이, 날짜, 사유를 기록한다.
- 금액은 원 단위 정수, 달력 날짜는 매장 현지 날짜(Asia/Seoul), 생성/변경 시각은 시각대가 명시된 시간값으로 다룬다. 날짜 값을 서버/브라우저 시간대 변환 때문에 전날/다음 날로 바꾸지 않는다.
- 삭제/수정 시 기록 ID와 일시를 남기는 감사 이력을 만든다. 마감 승인 후 수정도 같은 이력에 기록한다.

### 4.2 수업 중 초기 자료와 기록 보존

- 수업 중에는 제공 자료를 `가상 예시 데이터`로 사전 준비한다. 제공된 엑셀과 JSON을 둘 다 적재하지 않으며, 데모 데이터가 실매장 데이터로 오해되지 않게 모든 주요 화면에 예시 표식을 둔다.
- MVP에서 새로 입력하는 판매·비용·재고는 Supabase DB에 저장하고 다른 기기/세션에서 다시 열어도 유지한다.
- 브라우저 저장소(Local Storage)는 일시 입력 중 임시 값 정도에만 쓰며 영구 운영자료의 원본으로 삼지 않는다.
- 서버/DB 장애 시 오프라인 값을 자동 동기화하지 않는다. 미저장 안내를 보이고 같은 입력을 재시도할 수 있게 하여 이중 저장·덮어쓰기를 피한다.

### 4.3 파일 가져오기 — 수업 후 확장

- FRD대로 한 번에는 엑셀 또는 JSON 중 하나의 원천 형식만 가져온다. 같은 기록을 두 번 반영하지 않는다.
- MVP에는 가져오기를 구현하지 않는다. 확장 시 파일 전체를 검증하고 모든 행이 정상일 때 데이터베이스 트랜잭션으로 반영한다. 오류가 있으면 아무 행도 반영하지 않고 행 번호·필드·수정 이유를 표시한다.
- 파일은 허용된 형식/크기 검사 후 처리하고, 실제 운영 기록으로 반영된 뒤 원본 업로드 파일은 보관하지 않는다. 복구용 사용자 백업은 별도 흐름에서 명시적으로 만든다.
- 초기 제공 JSON은 약 3.5 MB, 엑셀은 약 0.5 MB다. Vercel 함수는 요청/응답 본문이 4.5 MB를 넘으면 413 오류를 반환하므로 업로드 한도를 4 MiB로 두는 것이 안전하다. 더 큰 자료를 지원해야 할 때는 비공개 임시 저장소로 직접 올린 뒤 처리하도록 별도 설계한다. 이 크기 제한은 현재 제공 자료에 적용 가능하나 향후 데이터 증가에 따라 재검토한다. [Vercel 함수 한도](https://vercel.com/docs/functions/limitations)
- 파일이 초과 크기, 손상, 미지원 형식, 필수 항목 누락, 잘못된 단위/값, 이미 반영한 원본인 경우 DB를 변경하지 않는다.

### 4.4 백업 및 복원 — 수업 후 확장

- 서비스 운영 기반 복구: Supabase Pro의 자동 일일 백업(현재 요금 안내상 7일 보존)을 사용한다. 이는 서비스 장애·실수로 DB를 복구하는 인프라 백업이지, FRD의 점주가 내려받는 백업 파일과는 구분한다.
- Supabase 자동 백업은 PostgreSQL 데이터베이스 대상이며 Storage 파일 자체는 포함하지 않는다. 업로드 원본 파일을 보관하지 않고 임시 파일을 처리 후 삭제하므로 주요 업무 기록은 DB 백업 범위에 둔다. [Supabase 데이터베이스·백업 안내](https://supabase.com/docs/guides/database/overview)
- 앱 사용자용 백업/복원은 수업 후 확장 기능이다. 백업은 로그인된 점주가 현재 매장 전체 자료를 버전 표시가 있는 JSON 파일로 내려받게 하고, 복원은 업로드 파일 검증 → 포함 자료·기준 날짜 미리보기 → 사용자 확인 → 전체 교체를 한 트랜잭션으로 수행하도록 한다. 기존 자료를 자동 병합하거나 자동 덮어쓰지 않는다.
- 복원 확인 직전 현재 DB도 안전 지점으로 백업/복제하고, 검증 또는 반영 실패 시 기존 운영자료는 그대로 유지한다. 파일 구조/버전 불일치, 손상, 기준 ID 연결 오류, 승인 취소는 복원하지 않는다.
- 내려받은 사용자 백업은 점주의 관리 기기에 저장한다. 앱 서버·공개 저장소·GitHub에 자동 보관하지 않는다. 복원 오류를 재현하려고 업로드 내용을 로그에 남기지 않는다.
- 자동 백업 보존 7일과 앱 다운로드 백업은 목적이 다르다. 장기 보관 기간·수동 백업 주기는 사업 운영 정책으로 추후 지정해야 한다.

## 5. 정보 보호

- **로그인·권한:** 점주 이메일 OTP 계정만 허용하고 공개 회원가입은 끈다. 모든 업무 화면·쓰기 요청은 서버에서 사용자 세션을 확인한다. 세션 만료 시 저장 작업을 거부하고 다시 로그인 안내를 한다.
- **행 단위 접근 제어(RLS):** 데이터베이스의 각 업무 표에 RLS(Row Level Security, 사용자가 볼 수 있는 행을 DB에서 제한하는 기능)를 적용한다. 현재는 점주 계정이 소유한 한 매장 자료만 읽고 쓰게 한다. 프런트엔드 버튼을 숨기는 것으로 권한을 대신하지 않는다. Supabase는 노출된 표에 RLS를 켜고 실제 권한을 검토하도록 권고한다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **비밀 키:** Supabase 관리자/서비스 키, 데이터베이스 암호, SMTP 키는 Vercel 서버 환경 설정에 저장한다. 브라우저로 전달되는 공개 변수나 GitHub 코드·샘플·스크린샷에는 넣지 않는다. 강한 관리자 키(service role)는 RLS를 우회할 수 있어 서버 이외에서 사용하지 않는다.
- **전송·저장:** 앱 통신과 DB 연결은 HTTPS/TLS를 사용한다. Supabase의 SSL 강제 설정을 켜고 데이터베이스 연결은 SSL을 사용한다. 비공개 백업/임시 업로드 버킷에 공개 URL을 만들지 않고 만료 시간이 있는 접근만 허용한다.
- **최소 정보:** 기능에 필요 없는 고객 이름/전화번호, 카드 정보, 직원 개인정보를 수집하지 않는다. 현재 자료에는 매장 운영 정보와 공급사 정보만 사용한다. 계정에는 점주 이메일만 필요한 범위로 보유한다.
- **로그:** 인증/오류 코드, 요청 식별자, 처리 시간만 남긴다. 판매 금액, 재고 사유, 로그인 토큰, 백업/업로드 본문은 일반 로그에 쓰지 않는다. 로그 접근은 관리자에게 제한하고 정해진 보존 기간 뒤 지운다.
- **관리 계정 보호:** GitHub·Vercel·Supabase 관리자 계정은 2단계 인증(MFA)을 켜고 접근 가능한 운영자를 최소화한다. 프로덕션과 Preview 환경 변수·데이터베이스를 분리하고, Preview는 가상 예시 데이터만 사용한다.
- **공급망·코드 보호:** 의존성 잠금 파일과 DB 마이그레이션을 GitHub에 저장하고, 비밀 파일·데이터 덤프·사용자 업로드 파일은 `.gitignore`한다. 프리뷰 URL에 실데이터를 연결하지 않는다.

Supabase Storage는 비공개 버킷의 내려받기에도 접근 정책을 적용할 수 있고, 서비스 키는 해당 정책을 우회하므로 외부 노출을 막아야 한다. [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control), [Supabase 비공개 버킷](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## 7. 배포 방법

1. 코드는 개인 또는 조직 GitHub 저장소에 보관한다. 운영 데이터와 비밀 키는 저장소에 커밋하지 않는다.
2. 기능 변경은 작업 브랜치에서 진행하고 Pull Request(변경 검토 요청)를 만든다.
3. GitHub 저장소를 Vercel에 연결한다. 작업 브랜치/PR마다 Preview 배포를 만들고, 검토용 데이터베이스에는 가상 샘플 데이터만 연결한다.
4. 체크 항목(형식·타입 검사, 계산 단위 검사, 입력 검증, 인증/RLS, 화면 흐름, 작은 화면 대응)이 통과하고 사용자가 Preview를 확인한 뒤에만 기본 운영 브랜치에 병합한다.
5. 기본 운영 브랜치 병합을 Vercel Production 배포로 연결한다. 도메인·HTTPS, 서울 함수 리전, 프로덕션 환경변수, Supabase 서울 프로젝트 및 RLS 적용 여부를 사전 확인한다.
6. 배포 직후 로그인, 판매 입력/병합/수정, 손익·재고 반영, 새 세션에서 재조회, 권한 없는 접근 차단을 확인한다. 실패하면 이전 배포로 되돌리고 DB 마이그레이션은 데이터 복구 계획에 따라 별도로 처리한다.
7. Vercel은 Git 연결 후 변경별 Preview와 프로덕션 브랜치 배포를 지원한다. DB 구조 변경 이력도 Git에 남기고 검토 후 운영 DB에 적용한다. [Vercel Git 배포](https://vercel.com/docs/git), [Vercel 배포 환경](https://vercel.com/docs/deployments/overview)

## 8. 확인 방법

TRD 구현 후 아래 방식으로 요구 준수를 확인한다. 문서 작성 단계에서 코드를 실행하거나 테스트한 것은 아니다.

### 계산·자료 검증

- 판매 2×4,500−500=8,500원, 동일 키 병합 시 수량 3·총액 14,000원·할인 500원·순매출 13,500원 예시를 자동 계산 검사와 화면 입력으로 확인한다.
- 메뉴 마진 예시 판매가 4,500원−식재료 1,300원−포장 150원=3,050원, 마진율 약 67.8%를 확인한다. 결제수수료·임차료·정규 인건비가 메뉴별 제품 마진에 섞이지 않아야 한다.
- 실제 손익 예시 순매출 10,000원−소비 원가 3,000원−실제 지출 2,000원=확인 가능한 5,000원을 확인하고 수수료 미제공 경고를 확인한다.
- 월 계획, 월 계획을 날짜에 나눈 과거 행, 새로 입력한 실제 비용을 대조해 중복 합산되지 않음을 확인한다.
- 재고 40+20−15−2=43, 실사 41 입력 시 −2 조정 후 41이 되는 것을 확인한다. g/ml/개 단위 오류와 음수 잔량 안내도 확인한다.
- 원천 예시의 공란, 0, 미마감일, 기간 끝 날짜, 과거 원가 스냅샷을 각각 유지하는지 확인한다.

### 기능·오류 검증

- 요구된 사용자 흐름(마감 홈→판매→수익성→손익→재고→마감 승인)을 PC·태블릿·모바일 화면 폭에서 직접 점검한다.
- 저장 후 새로고침/다시 로그인한 뒤 입력이 남는지 확인한다. 수정·삭제 취소·승인 후 수정 이력도 점검한다.
- 필수값 누락, 범위 초과 할인, 0/음수 수량, 잘못된 단위, 네트워크/DB 오류, 잘못된 파일, 손상 백업, 접근 불가 세션을 각각 확인한다.
- 등록되지 않은 계정과 로그아웃 상태에서 매출/비용/재고 데이터를 읽거나 바꿀 수 없는지 확인한다. 다른 계정 데이터가 응답/캐시에 섞이지 않는지 확인한다.
- Preview 환경이 가상 자료만 사용하고 Production 환경 변수와 DB를 공유하지 않는지 확인한다.

### 속도·운영비 검토

- 현재 제공 자료 규모를 초기 기준으로 기간/메뉴/채널 필터가 적절한 시간 내 응답하는지 측정한다. 실제 기준 시간은 구현 시 수업용 목표치를 정하고 측정 결과로 보고한다.
- Supabase DB 크기·쿼리 시간·연결 사용량, Vercel 함수 실행 시간·요청량·전송량을 월별 확인한다. 이 앱은 로그인 점주 한 명의 마감 업무이므로 높은 동시 접속·실시간 갱신은 최적화 대상이 아니다.
- 현재 안내 기준의 시작 비용은 월 약 $45이며 세금·메일 전송·사용량 증가분은 포함하지 않는다. 첫 실사용 전에 가격·백업 보존·프로젝트 중지 조건을 다시 확인한다.
